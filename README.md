A job artifact in GitHub Actions is a file or collection of files produced by a workflow job that you save so you can access or use them later.

Think of it as saving the output of a job rather than letting it disappear when the job finishes.
Example
Imagine your CI/CD workflow has two jobs:
1. Build: Builds your application and generates a file, such as app.zip.
2. Deploy: Downloads app.zip and deploys it to AWS.


GitHub provides two commonly used actions for handling artifacts:
1. actions/upload-artifact
Uploads files or folders generated by a job and saves them as an artifact.

For example, after your build job generates app.zip, you can upload it:
- name: Upload build artifact
  uses: actions/upload-artifact@v4
  with:
    name: my-app
    path: app.zip


Here:
- name: The name given to the artifact (my-app).
- path: The file or folder you want to upload (app.zip).
2. actions/download-artifact
Downloads an artifact that was previously uploaded, allowing another job to use its files.
- name: Download build artifact
  uses: actions/download-artifact@v4
  with:
    name: my-app


Here, name: my-app tells GitHub which artifact to download.

In GitHub Actions, job outputs are values that one job makes available to another job in the same workflow.

Think of them as a way for jobs to pass small pieces of information to each other.
Example
Imagine you have two jobs:
- Job 1 – Build: Generates a version number.
- Job 2 – Deploy: Needs that version number to deploy the correct build.
The build job can expose the version number as an output, and the deploy job can read it.

Dependency caching in GitHub Actions means saving downloaded project dependencies so that future workflow runs can reuse them instead of downloading everything again.

It helps make workflows faster and more efficient.
GitHub provides the actions/cache action.


hashFiles() is a GitHub Actions function that calculates a hash (a unique-looking fingerprint) based on the contents of the specified file.

For example:

Imagine your package-lock.json initially contains dependencies for:
- React
- Express
- Axios
GitHub calculates a hash and uses it to create a cache key.
Now suppose you add another dependency, such as Lodash.

The contents of package-lock.json change, so its hash changes.

The resulting cache key will also change.
This means GitHub will not mistake the old dependency cache for an exact match to the new dependency set.
